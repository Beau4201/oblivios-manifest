## Vendor modules for lynx and stallion (2026-10-14)

- `adevtool generate-all` for `lynx` (`CP3A.261005.002.A1`) and `stallion` (`CP3A.261005.005`), with
  `-k` so that only one device keeps its unpacked images. Both pins in
  `vendor/google_devices/<device>/adevtool-version-check.mk` equal the `vendor/adevtool` HEAD
  (`12af213a865b`).
- **Defect in `memory/zram-size` and `memory/cached-process-cap` found by this run.** Those patches
  dropped the stock values from the inclusion lists; adevtool includes unknown entries, so the
  regenerated modules carried `mmd.zram.size=50%` (a second value fails `post_process_props.py`) and
  `config_customizedMaxCachedProcesses=1024` in the vendor overlay (which overrides the framework
  value of ADR-151). Both are now on the exclusion lists. The package notes of 2026-10-10 said
  `generate-all` was never run with the changed lists; this is the run.
- Evidence: a verified `stallion` run (before `--noVerify`) failed the comparison with upstream's
  FileTreeSpec with exactly two changed entries, `values.xml` of the vendor overlay and
  `product.prop`. After the exclusions both devices were regenerated with `--noVerify`; against the
  unmodified regeneration of `lynx` (which passed the FileTreeSpec) the only differences are
  `config_customizedMaxCachedProcesses` and `mmd.zram.size=50%`, plus the pin.
- `--noVerify` makes adevtool write `$(warning` instead of `$(error` in the pin file; both files were
  put back to `$(error` by hand so that a stale pin still fails a build in one second.
- New upstream value: `mmd.zram.writeback.limit.enabled=true` with `max_bytes_per_day=25769803776`
  (it was `false` before). It bears on `MEM-005` (flash writes at 100% zram); not measured.
- Previous modules and the unmodified regeneration are kept beside the tree on the build server
  (`backup-vendor-pre-2026100600`).
