## First signing attempt of 2026092501 (2026-09-26, failed, nothing published)

- Live `~/sign-ota.sh` on the signing host has sha256 `8113277f...a00f`, not the repo's
  `199dfda7...2748`. It still uses the pre-rename `aegisos` shared-directory paths `unsigned` and `signed` (virtiofs tags
  `build-unsigned` ro / `build-signed` rw, the same tags the build server mounts under
  the `sovereignos` name with the reverse modes, so the shared directories are intact). After
  replacing `aegisos` with `sovereignos` in those three path lines the live file hashes to the repo hash, so the two
  differ only in those three path lines; the live file was run unchanged. The signing host's
  `release-tools` copy was not compared.
- Both candidate hashes matched. Signing (`generate-release.sh`) ran; the following
  independent check, `check_ota_package_signature.py` (regular python3, not hermetic),
  was `Killed` (SIGKILL) and the script aborted as designed: `FAILED`, "nothing published",
  vault closed, tmpfs swept, VM powered off. The signed OTA lived only in the run directory
  the exit trap removes, so the signing has to be repeated. Ceremony log entry:
  `ceremony-log/2026092501.log` (`independent re-verification of the signed OTA failed`).
- Cause established (same day, from the signing host's previous-boot kernel log,
  `journalctl -k -b -1`): `python3 invoked oom-killer`, `Out of memory: Killed process 14936
  (python3) total-vm:2839532kB, anon-rss:1840356kB`, i.e. the verification process alone held
  about 1.84 GB of the host's 1.9 GB RAM. The earlier three candidates passed with very little
  margin. Fix chosen: more RAM for the signing host (no script change, no swap, since swap would put
  process memory on unencrypted disk next to the ceremony); the original suspicion below is kept
  for the record.
- (Original note, before the log was read) Not established: the cause of the kill. The log's `verify.log` was in `/dev/shm` and is gone.
  Leading suspicion is the kernel OOM killer, since the signing host has 1.9 GB RAM and this step
  extracts a ~1.4 GB `payload.bin` and runs `delta_generator`; against that, three earlier
  candidates (OTA 1.427-1.432 GB) passed this step on the same host and this candidate is only
  0.4-0.8% larger. The disk watchdog is not a likely killer (shared pool had 35 GB free, its
  `pkill` patterns do not match this command). Previous history: `2026081901` also failed this
  step twice on 2026-08-22 before succeeding (TMPDIR and PATH fixes, see the storage root-cause
  report).
